## 1. 概述

判据项 40 条，测试点 64 个，用例 64 条。
测试点按类型：单元 16、接口 44、端到端 4；按优先级：P0 31、P1 27、P2 6。

- **范围**：范围：booking-agent 新增的 agent 层，包括 4 个 /agent/** 接口与 SSE 事件、8 个工具的参数校验与鉴权、待确认动作生命周期、booking_request 幂等以及确认与取消互斥、会话存储与 20 轮窗口、限流、超时与工具上限、LlmClient 二选一与 FakeLlmClient、OpenAiLlmClient 中与 SDK 无关的部分，以及聊天面板主流程。测试类型三类，不设 manual：unit = 单元测试，不启动 Spring 容器，不连数据库和 Redis（纯逻辑 + Mockito：会话截断与回放、参数解析校验、待确认动作状态规则、提示词组装、假模型规则等）；api = 集成测试，@SpringBootTest + Testcontainers（MySQL、Redis），使用 FakeLlmClient 按剧本返回工具调用，经 HTTP 调 /agent/** 接口，断言返回、SSE 事件、库表和 Redis；e2e = 端到端测试，Playwright 驱动静态页聊天面板，e2e profile 使用假模型。精简原则：同一规则只是参数不同的，合成一个参数化测试点；e2e 只保留覆盖演示脚本的 4 条主流程（TP-051～TP-054）；e2e 已覆盖的正向流程，api 层主要测反向、异常和边界，但确认接口本身的正向结果（支付、取消后的数据变化和提示语）仍在 api 层断言（TP-060），失败时能直接定位到确认接口。现有业务规则（计价、冲突检查、支付和取消条件、点餐计价）只测 agent 层如何复用：报价金额等于下单金额，预检与现有 SQL 条件一致，确认时调用现有 Service 并比对金额。三类测试条件（输入取值、业务规则、状态流程）都有覆盖。优先级：G2 写操作安全（未确认不下单、越权为 0、重复确认只有一单、价格变动拒绝、取消与确认互斥、并发与死锁不出 500）为 P0；G1 主流程为 P0 或 P1；其余为 P1 或 P2。
- **不测**：1）真实模型评测：PRD §8 的 20～30 条评测集、任务完成率 ≥90%、追问是否恰当、越权尝试拦截率、首字 3 秒内，以及带加密推理项的多轮真实回放，由单独的评测脚本 AgentEval 承担（design §6「PRD 成功指标：完成率 ≥90%」行），不作为自动化测试点。2）OpenAiLlmClient 的流式事件和用量字段的取法（design §4.8「流式」「用量日志」行）不设测试点。请求参数（model、store=false、include 加密推理、8 个工具）和无 raw 项的回放转换预期值确定，由 TP-055、TP-056 覆盖；从 SDK 对象读出参数、构造输入项的方法在用例阶段按 openai-java 文档确定（GAP-11）。3）现有业务规则本身（R-093 逐晚计价与默认价、R-104 区间冲突、R-106 支付 15 分钟、R-110 取消与退款、R-126/R-127 点餐计价与菜品状态）已由现有 285 个测试覆盖，不重复；回归以 mvn -B clean verify 全量通过为准。4）前端非主流程不设 e2e，对应的服务端行为由 api 测试点覆盖：卡片「已取消」「已失效」显示、倒计时、员工不显示入口、「新对话」按钮、429/503 提示、样式与遮挡。5）演示彩排（真实模型与 fake 各走一遍、5 分钟内走完）属于人工演练，不进测试方案。6）日志内容（PRD §5 可观测、日志不含完整个人信息）由代码评审检查。7）设计接受的已知限制（design §5）不测：同一会话并发两条消息不加锁（D-010）、限流 INCR 与 EXPIRE 非原子（D-013）、多实例会话一致性。

## 5. 风险与需求缺口

**风险**：1）并发测试点（TP-009、TP-012、TP-016）依赖 InnoDB 唯一键等待和死锁的时序，走哪个分支不固定。断言只能写成状态集合与行数，需要重复执行验证稳定性；异常转换的每个分支另由 TP-057、TP-058 单元测试确定性覆盖。2）用例跑在零点附近时「今天」「明天」会变，日期必须在用例内现算。3）假模型下状态行一闪而过，e2e 对工具状态的断言改为读 /agent/chat 响应体里的 status 事件，不等页面文字。4）右下角悬浮按钮可能挡住现有 6 条 e2e 的点击，需要全量跑现有 e2e。5）openai-java 与 Jackson 的版本冲突要到真正建客户端时才暴露，TP-048 是唯一的自动化防线。6）单个用例 1 分钟内发超过 10 条消息会触发限流，这类用例直接在 Redis 预置数据：TP-012 直接写入待确认动作，TP-063 直接 RPUSH 预置 21 轮会话，都不经 /agent/chat。7）假模型按句式规则匹配，e2e 文案和 FakeLlmClient 规则对不上时会落到「能力说明」分支；e2e 文案要和 TP-050 的规则用例保持一致。
