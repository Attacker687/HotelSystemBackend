## 1. 概述

判据项 50 条，测试点 49 个，用例 51 条。
测试点按类型：单元 8、接口 37、端到端 4；按优先级：P0 25、P1 23、P2 1。

- **范围**：范围：booking-consistency 三批交付带来的行为变化。M1 = POST /order 的 Idempotency-Key（接收与格式、请求方绑定、请求摘要、重复请求的返回、失败记录规则、与助手确认共用 booking_request、7 天清理、app.js 携带 key）；M2 = room_inventory 每日库存（全部占用与释放入口、按晚判定、改期差集、回填脚本与冲突、异常转 409、助手查空房与报价改用库存表、营收口径不变）；M3 = HotCache（房间详情与价格日历的 Cache Aside、提交后删 key、随机 TTL、空值缓存、故障降级、开关、不缓存房态与订单）；G4 = 现有用例回归与 5.1 列出的调整。测试类型三类，不设 manual：unit = 单元测试，不启动 Spring 容器，不连数据库和 Redis（纯逻辑 + Mockito：OrderRequestService 分支与摘要、occupy 的异常转换与升序、HotCache）；api = 集成测试，@SpringBootTest + Testcontainers（MySQL、Redis），经 HTTP 调接口，断言返回、库表、Redis 和 SQL 计数；e2e = 端到端测试，Playwright 驱动静态页（网页下单携带 Idempotency-Key、网络重试复用 key、连点只出一单、取消后重订）。批次标注：每个测试点的 story 字段写批次 M1、M2、M3（目前没有 stories.json，Story 拆分后可改写成 M1-S2 之类的编号）；TP-049 是跨批次的最终门禁，写 M1、M2、M3。精简原则：同一规则只是参数不同的合成一个参数化测试点；e2e 只留 4 个主流程点，且全部落在现有 TC-132、TC-133、TC-137 的步骤里加断言，不新增浏览器用例（design §5.1：浏览器用例保持 10 条）；e2e 已覆盖的正向流程，api 层主要测反向、异常和边界，但库存与幂等的正向结果（占用行数、订单号一致）仍在 api 层断言库表。三类测试条件都有覆盖：input（key 格式与内容字段、按晚边界、TTL 与保留期边界）、rule（判定顺序、异常转换、缓存规则）、state（SUCCESS/FAILED 重放、订单有效性与占用的联动、缓存命中与失效）。优先级：G1、G2 的资金与数据正确性（重复下单、超卖、占用泄漏、越权复用）为 P0；缓存与批次回归为 P1，只有「更新后读到新值」「房态不缓存」为 P0；开关为 P2。
- **不测**：1）性能压测与性能指标（goal.md 不包括项）；50 并发只验证正确性，不测吞吐与耗时。2）支付、取消接口本身的请求幂等（goal.md 不包括项），只测它们对占用的影响。3）上线与回滚步骤（design §5.7）、停写窗口、ALTER 迁移脚本的手工执行：脚本手工执行，不进自动化（GAP-06）；回填 SQL 脚本本身进 api 测试（TP-028、TP-029）。4）Redis 整体停止时登录态读取失败返回 401（D-015，不改 LoginFilter）：只做缓存键故障注入，不停 Redis 容器。5）缓存已知竞态（读者写回旧值，最长 40 分钟，design §4.3.4）、热点键互斥重建（D-004）、新建房间不删缓存（D-019）：设计接受的限制，不测。6）@Valid 校验失败发生在进入服务之前、不占用 key（design §4.1.1）：由 Spring MVC 校验顺序保证，不单设测试点。7）直接改库（运维 SQL、夹具桥）不同步占用或缓存（design §5.6、§4.3.4）：约定通过接口改状态，用 I1、I2 核对。8）CI 工作流文件不改（design §5.7）：由代码评审确认，不设测试点。9）助手卡片 10 分钟过期、助手限流、会话存储等 booking-agent 既有规则：已有测试覆盖，只作回归。10）日志内容（库存冲突、幂等命中 INFO，缓存命中 DEBUG，不含个人信息，D-020）：由代码评审检查。11）既有业务规则本身（R-093 逐晚计价、R-110 取消条件、R-106 支付 15 分钟等）已有现有用例覆盖，不重复。

## 5. 风险与需求缺口

**风险**：1）并发测试点（TP-002、TP-017、TP-018）依赖 InnoDB 唯一键等待与死锁的时序，走哪个分支不固定：断言写成状态集合与行数（每个响应要么 200 同一订单号、要么 409），不断言哪个线程赢；TP-018 重复 20 轮，需重复执行验证稳定性。2）真实死锁与锁等待超时无法在集成测试里确定性制造（GAP-03）：转换分支由 TP-030 单元测试确定性覆盖，TP-032 用 @SpyBean 抛 Spring 异常验证 HTTP 层结果。3）HikariCP 默认最大 10 个连接（design §5.6）：TP-002 的 10 个同 key 请求在唯一键上等待时各占一个连接，TP-017 的 50 并发请求排队等连接，可能因连接池等待而变慢，用例超时时间要留足。4）Fixtures.roomOrder 自动写占用依赖 insert ignore，同房同晚多张种子单只留先到者：统计类旧用例若依赖「每张订单都有占用」会漏报，需用 I1 核对（TP-035）。5）用例跑在零点附近时「今天」「明天」会变，日期必须在用例内现算；提前结束的「今天」取哪个时钟没写（GAP-04）。6）TP-048 的 tc117 断言「两次读取条数相同」可能不稳定，方案允许改为小于等于（GAP-12）。7）e2e 夹具桥直接改订单时刻与创建时间，不会同步占用日期；释放按 order_id 删除，不依赖日期，所以不受影响（design §5.1）。8）app.js 的 crypto.randomUUID 回退路径在 localhost 安全上下文下走不到，TP-016 用 addInitScript 把 randomUUID 置为 undefined 来触发。9）超时取消改为 select for update 后逐单更新，tc069、tc075 并发用例若出现死锁会表现为 409 而不是原断言的状态，需关注 TP-034 的稳定性。
